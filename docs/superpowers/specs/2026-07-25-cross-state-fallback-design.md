# Cross-state reference fallback — design

> **Amended by `2026-07-30-cross-state-backend-probe-design.md`:** state
> acquisition now asks the backend from a scratch directory. The
> workspace-dependent probe this design led to could never fire in a
> clean-workspace pipeline, so state-aware runs silently degraded every
> reference to a literal. The fallback semantics below stand.

## Problem

When cross-state reference binding is enabled, a generated env root emits a
`data "terraform_remote_state"` block for every root it references. If a
referenced root has no state, Terraform halts on the data-source read. Adopting
any one resource type therefore requires every root it references to already be
applied.

Goal: fall back to the literal ID from the tfvars when the referenced state
item is unavailable, automatically, with the pipeline reporting where each
fallback occurred.

## Constraints (from the requester)

- **No declaration list.** Fallback must be automatic. A per-reference opt-in
  registry is explicitly rejected.
- **The pipeline reports fallbacks.** Visibility, not ceremony. No
  acknowledgement gate, no policy file.
- Serves both incremental adoption (roots adopted one at a time) and permanent
  partial adoption (references to resources infrawright will never manage).

## Established facts

Verified by reading the source:

- The tfvars carry the literal tenant ID. Cross-state binding is a **separate
  overlay** (`<resource>.generated.expressions.json`) merged over the items by
  `ApplyExpressionBindings` (`go/internal/envgen/expression_bindings.go:909`).
  The literal is never discarded. **Dropping a binding is therefore already the
  fallback** — the literal underneath survives untouched.
- Transform-time fallback already exists and is already reported.
  `DeriveGeneratedBindings` (`go/internal/tfrender/transform_artifacts.go:843`)
  skips with a counted reason for `self_reference`, `missing_lookup`, and
  `key_map_unavailable`; `bindValue` (`:785`) emits the literal quoted string
  for any individual ID absent from the referent's key map, mixing bound and
  literal elements in one list. Notes are recorded via `b.note` / `b.count`.
- `renderRemoteStateBlocks` derives its block list from the surviving bindings
  (`remoteStateReferencesForBindings`), so filtering a binding removes its
  `data` block as a consequence rather than as separate work.
- `stage-imports` already has a `--state-aware` mode
  (`go/internal/adopt/import_staging.go:72`) — consulting state mid-pipeline is
  an established pattern, not a new concept.

Verified empirically (scratch Terraform, local backend):

| case | behaviour |
|---|---|
| state present, map key missing | `try(..., literal)` falls back cleanly |
| state absent entirely | `Error: Unable to find remote state` — plan halts, `try()` cannot catch it |

## Unverified premise — must be established first

That a real infrawright-generated env root actually hits the state-absent
failure has **not** been reproduced end to end. It is inferred from the emitted
`data` blocks plus the Terraform behaviour above. No implementation should
begin until this is reproduced against generated output.

## Proposed approach

The fix lives in `gen-env`:

1. `gen-env` gains an opt-in state probe, mirroring `stage-imports --state-aware`
   so the default path keeps working with no backend access.
2. For each root that `remoteStateReferencesForBindings` would emit a `data`
   block for, probe whether its state object exists.
3. Filter out bindings whose referenced root has no state, before
   `ApplyExpressionBindings`. The tfvars literal survives.
4. No `data` block is emitted for that root, as a consequence of (3).
5. Report each filtered binding through the existing notes channel.

Residual plan-time case worth deciding during planning: a referenced root has
state, but the item was renamed or removed since transform bound it, so the key
is missing from the output map. `try(..., <literal>)` would catch this one.
Whether to emit it is a separate call — it trades a loud failure for silent use
of a stale ID, which is in tension with the repository's fail-loud posture.

## Open design questions for the plan

- Report format and channel: reuse the transform notes shape, or a distinct
  gen-env report?
- Probe failure handling: backend unreachable is not the same as state absent.
  Absent should fall back; unreachable should almost certainly fail closed.
- Should the probe be per-root existence only (cheap) or read the output map
  (exact, enables key-level decisions at generation time)?
- Determinism: generated bytes now depend on backend state. What does this mean
  for `check-demo` drift and the byte-golden contract?

## Out of scope

Production engine changes beyond `gen-env` and its direct helpers. Per
`AGENTS.md`, a new `overrideKeys` entry or a change to transform, lineage, or
the assessment engine means stop and ask.
