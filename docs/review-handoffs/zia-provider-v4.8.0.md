# ZIA Provider 4.8.0 Review Handoff

## Intent

- Refresh only the ZIA pack and checked-in provider schema from `4.7.26` to
  `4.8.0`.
- Admit six existing-resource scalar fields that now have matching provider
  schema, Read, and expand evidence: `eun_template_id`,
  `exclude_context_shield_end_point`, and `is_eun_enabled` on both firewall DNS
  and firewall filtering rules.
- Preserve endpoint-application safety with three explicit, generic controls:
  raw-transform drops; provider-version-scoped `match_any_nonempty` adoption
  rules that fail endpoint-bearing items before the Oracle; and pack
  `projection_omit` policy for provider state and generated import config.
- Keep ZPA, the AST/source-analysis implementation, and new ZIA resource
  onboarding unchanged.

## Expected Delta

- Expected behavior change: firewall DNS/filtering transforms retain
  `eun_template_id`, `exclude_context_shield_end_point`, and `is_eun_enabled`.
  Raw transform omits endpoint application/application-group fields. Adoption
  rejects only endpoint-bearing DNS/filtering/IPS/SSL items before invoking the
  provider Oracle; endpoint-free items remain eligible. If representable
  endpoint provider state or generated import blocks reach projection, pack
  policy removes both blocks.
- Expected report/count/coverage changes: six provider-missing holds are
  removed; four DNS/filtering endpoint holds are reclassified; two IPS and two
  SSL endpoint holds are explicit; four registry resources gain version-scoped
  unsupported adoption metadata. No readiness or OpenAPI coverage claim
  changes.
- Expected generated-output changes: the fresh provider schema adds nine
  resources and ten data sources. Existing resource deltas are DNS/filtering
  scalar and endpoint fields, IPS endpoint fields plus `eun_template_id`
  becoming Optional-only, SSL endpoint fields, and DLP web-rule `action`
  becoming Optional-only.
- Expected no-op areas: the nine new resource types are not in the ZIA registry
  and therefore are not collection/adoption/module targets. ZPA and AST work
  are unchanged.

## Invariants Claimed

- Evidence must not be silently dropped: endpoint exclusions use explicit raw
  `drops`, pre-Oracle source-backed unsupported rules, pack projection policy,
  and shared holds. No Zscaler field name is embedded in generic Go logic.
- Generic matcher evidence must not outrank source-backed evidence:
  `match_any_nonempty` can only select a provider-version-scoped,
  evidence-linked unsupported rule; it cannot create a support claim or alter
  source-operation lineage.
- Source precedence/provenance must remain explicit: provider and SDK tags,
  commits, schema digest, and fixture evidence links are versioned.
- Ambiguity must stay classified instead of being coerced to success: the new
  endpoint declarations are not treated as behavioral support; populated raw
  endpoint fields become a visible unsupported disposition before Oracle.
- Provider-readiness counts must stay explainable: only raw provider schema
  inventory counts change; no new registry readiness status is asserted.
- Adoption safety invariants: the sandbox order-127 and URL-filtering ISOLATE
  guards were re-pinned to `4.8.0` only after confirming their provider source
  files are byte-identical to `4.7.26`. Endpoint-free DNS/filtering items retain
  all six admitted scalars, while endpoint-bearing items cannot invoke provider
  Read or publish artifacts.

## Known Deferrals

- Deferred work: onboard the nine new ZIA resources and ten data sources.
- Reason it is safe to defer: they are schema-visible but absent from the pack
  registry, so this change makes no collection or adoption claims for them.
- Follow-up owner or trigger: a separate provider-resource adoption branch with
  API mappings, fixtures, source witnesses, and live round-trip evidence.
- Deferred work: endpoint application/application-group support on DNS,
  filtering, IPS, and SSL.
- Reason it is safe to defer: raw transform omits the fields, populated raw
  assignments fail closed before provider Read, and both post-Read projection
  surfaces omit representable blocks. DNS/filtering/SSL resource Read calls the
  full data-source flatteners, whose object shapes do not fit the resource
  blocks; IPS declares the blocks but neither expands nor reads them. This is a
  deliberate unsupported disposition, not a claim that adoption silently
  preserves endpoint assignments.
- Follow-up owner or trigger: an upstream provider fix plus a live
  create/import/read/no-op-plan proof. Schema-derived modules still expose the
  optional provider-declared inputs; consumers must not set them before that
  proof.

## Review Focus

- Highest-risk files or paths: the regenerated ZIA schema, four rule overrides,
  shared adoption holds, provider-versioned registry guards and projection
  policy, generic unsupported predicate validation/classification, generated
  config whole-block omission, and generated compatibility fixtures.
- Specific assumptions to attack: only the six scalar holds are safe to close;
  populated endpoint fields always stop before Oracle while absent/null/empty
  fields remain eligible; projection omissions remove whole optional blocks but
  cannot remove required blocks; version-scoped sandbox and ISOLATE guards
  still match `4.8.0`; no new resource became registry-enabled accidentally.
- Source evidence the reviewer should verify: resource schema declarations,
  direct scalar `d.Set` and expand assignments, endpoint flattener call sites
  and shapes, absent IPS endpoint read/expand assignments, and unchanged
  sandbox/URL-filtering source files.
- Generated artifacts the reviewer should compare: reproduce the provider
  schema digest; verify the 83/115 counts and exact nine/ten additions; inspect
  parity and module compatibility drift for provenance-only or expected schema
  changes.
- Edge cases that could silently overclaim, remap, drop, or weaken evidence:
  raw camelCase endpoint objects versus the single-block set schema; optional
  module inputs despite pre-Oracle rejection; empty collections versus
  populated false/zero scalars in the generic predicate; whole-block generated
  config parsing around nested blocks/heredocs; stale provider-version
  predicates; treating schema presence as round-trip proof; accidental ZPA or
  AST drift.
